2. Training and tuning on Google Cloud

Organizing and ingesting training data

  • Tabular: BigQuery tables, read by AutoML and pipelines directly, or by custom code through the BigQuery Storage Read API (fast parallel reads into TensorFlow, PyTorch or pandas).
  • Unstructured: files in Cloud Storage plus a manifest. Custom training jobs see buckets as local paths through Cloud Storage FUSE (/gcs/my-bucket/...).
  • Managed datasets on Agent Platform hold image, video and tabular datasets with labels and splits, used by AutoML and for lineage.
  • Ingest from other systems with Dataflow, Datastream (database change data capture into BigQuery), Storage Transfer Service, or BigQuery Data Transfer Service.

Troubleshooting training failures

SymptomLikely causeFix
Job fails immediately with permission deniedThe training service account can't read the bucket or BigQuery tableGrant the job's service account the roles it needs (it's not your user identity)
Out of memory (host or GPU)Batch size too large, data loaded fully into memorySmaller batches, streaming input (tf.data, DataLoader), larger machine or more GPUs
Loss becomes NaNLearning rate too high, unscaled features, bad labels, log(0)Lower learning rate, normalize, gradient clipping, check data
Quota exceeded / resources unavailableGPU quota or capacity in the regionRequest quota, another region or accelerator, reservations or Dynamic Workload Scheduler
Job restarted and lost hours of workSpot preemption or maintenance without checkpointsCheckpoint to Cloud Storage regularly; resume from the latest checkpoint
GPU utilization lowInput pipeline bottleneckPrefetch, parallel reads, TFRecord shards, cache; profile with TensorBoard Profiler
Training accuracy high, validation poorOverfittingRegularization, dropout, more data, augmentation, early stopping
Both training and validation poorUnderfitting or bad featuresBigger model, better features, train longer

Hyperparameter tuning

Hyperparameter tuning jobs (powered by Vizier) run many trials of your training code with different values and optimize a metric your code reports (with the cloudml-hypertune helper or the metric reporting API).

  • Algorithms: Bayesian optimization (default), grid search, random search.
  • max_trial_count bounds cost; parallel_trial_count trades wall-clock time against quality: more parallel trials finish sooner, but Bayesian search learns less from earlier trials.
  • Use log scaling for learning rates, discrete values for layer counts, and early stopping of poor trials.
  • Simple alternatives: AutoML (tunes for you), BQML num_trials with hyperparameter ranges.

Fine-tuning foundation models

OptionUse
Supervised tuning of Gemini on Agent Platform (or from BigQuery ML)Managed, parameter-efficient tuning on JSONL prompt/response pairs; the tuned model gets its own endpoint
Open models from Model Garden (Gemma, Llama) with LoRA / QLoRA notebooks or managed tuningFull control of weights; deploy where you want
Reinforcement learning / preference tuningAlign to human preferences
Consider tuning only when prompting and grounding fall short and you have good labelled examples. Benefits: higher quality on a narrow task, shorter prompts (cheaper, faster), consistent format. Costs: data preparation, tuning jobs, re-tuning when the base model is updated, and evaluation work.

3. Hardware and distributed training

HardwareBest forWatch out
CPUClassic ML (scikit-learn, XGBoost on modest data), preprocessing, small models, low-volume servingSlow for deep learning
GPU (NVIDIA L4, A100, H100, H200, B200...)Most deep learning; flexible across frameworks; custom CUDA ops; inference with TensorRT or vLLMQuota and capacity; cost when idle
TPU (Cloud TPU v5e, v5p, Trillium, Ironwood...)Large matrix-heavy models in JAX, TensorFlow or PyTorch/XLA; large-batch training; high-throughput LLM serving at low costCustom ops not supported by XLA, heavy dynamic shapes, high-precision (float64) math and very small models fit poorly
Edge (phones, Edge TPU, Jetson)On-device inference, offline useNeeds quantized, small models
Accelerator generations change quickly. The exam tests the trade-off (CPU vs GPU vs TPU, and when TPUs don't fit), not the newest SKU.

Distributed training strategies

StrategyHowWhen
Data parallelismCopy the model to every device; split each batch; average gradients with all-reduceThe model fits on one device and you want speed. TensorFlow MirroredStrategy (one machine), MultiWorkerMirroredStrategy (many machines), TPUStrategy; PyTorch DDP
Parameter serverWorkers push gradients to parameter servers asynchronouslyLarge sparse models (embeddings), many CPU workers
Model parallelism (tensor, pipeline)Split layers or tensors across devicesThe model doesn't fit on one device
Sharded data parallel (FSDP, ZeRO)Shard parameters, gradients and optimizer states across data-parallel workersLarge models with data-parallel simplicity
Reduction Server (Agent Platform)Extra reducer nodes speed up all-reduce for multi-node GPU data parallel jobsNetwork-bound gradient synchronization
"Fits? Data. Doesn't fit? Model." If one copy fits on one device, scale out with data parallelism; if it doesn't, split the model.
More GPUs doesn't fix an input-bound job. If GPUs sit at 30% utilization, fix the data pipeline first. And with data parallelism, scale the learning rate or batch size deliberately: global batch = per-device batch × devices.

4. Accelerator memory calculator

A rough first estimate of whether a model fits on one accelerator, and therefore whether data parallelism is enough or the model must be sharded. Real usage also depends on activations, sequence length and batch size.

Bytes per parameter: 16-bit inference ≈ 2; int8 ≈ 1; int4 ≈ 0.5; full mixed-precision training with Adam ≈ 16 (weights, gradients, two optimizer states, master weights).

5. Lab: custom training, tuning and the registry

Placeholders: PROJECT_ID, BUCKET, region us-central1.

  1. Write a scikit-learn or XGBoost script that reads from BigQuery, trains, reports a metric with cloudml-hypertune, and saves the model to AIP_MODEL_DIR.
  2. Run it as a custom training job with a prebuilt container and a dedicated, least-privilege service account. Remove its BigQuery role once and read the 403 error: which principal does it name?
  3. Run a hyperparameter tuning job with 12 trials, parallel 3, a log-scaled learning rate and a discrete max depth. Compare with parallel 12: what changes in wall-clock time and best metric?
  4. Add checkpointing to Cloud Storage and rerun on Spot VMs; confirm it resumes after a restart.
  5. Upload the best model to Model Registry as version 1 with a prebuilt prediction container. Continue in the serving lab.

Clean up: delete jobs' output you don't need and the staging bucket contents.

What to look at: The best trial (7) wins on the reported metric auc_pr, which the training code must report. Four trials ran in parallel: faster, but each wave learns less from the previous ones. An INFEASIBLE trial usually means the code crashed or didn't report the metric for those values.

11. Common gotchas in one list

  1. The job runs as a service account, not as you: grant it the roles.
  2. Save models to AIP_MODEL_DIR so the platform can find them.
  3. Spot VMs need checkpoints or every preemption restarts training.
  4. Fits on one device → data parallel; doesn't → shard or split the model.
  5. Low GPU utilization is usually the input pipeline, not too few GPUs.
  6. TPUs don't fit custom CUDA ops, float64 or heavy dynamic shapes.
  7. More parallel trials finish sooner but search less adaptively.
  8. Use log scale for learning rates in tuning.
  9. Full fine-tuning needs ~8× the memory of 16-bit inference; LoRA and quantization cut it.
  10. Prebuilt containers before custom containers when the framework is supported.
  11. Interpretability requirements drive model choice in regulated domains.
