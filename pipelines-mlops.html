1. End-to-end ML pipelines

A pipeline turns notebook steps into a repeatable, versioned, automated workflow: ingest → validate data → transform → train → evaluate → validate the model → register → deploy → monitor. Each run records lineage, so you can answer "which data and code produced the model in production?"

Orchestrators

OrchestratorChoose when
Agent Platform PipelinesDefault for ML: serverless, runs Kubeflow Pipelines (KFP) v2 or TFX pipelines, automatic lineage in ML Metadata, caching, Google Cloud Pipeline Components, scheduling
Managed Service for Apache Airflow (formerly Cloud Composer)Orchestrating whole data platforms: many systems, ETL schedules, cross-team DAGs. It can trigger ML pipelines, but isn't ML-aware (no artifact lineage)
Ray on Agent PlatformPython-native distributed data processing, training and tuning (Ray Data, Ray Train, Ray Tune) on a managed Ray cluster
Kubeflow Pipelines on GKESelf-managed open source on your own cluster

TFX components (TensorFlow Extended)

ComponentJob
ExampleGenIngest and split data
StatisticsGen, SchemaGen, ExampleValidatorData statistics, an inferred schema, and anomaly detection (TensorFlow Data Validation, TFDV)
TransformTensorFlow Transform: full-pass preprocessing (vocabularies, normalization) exported into the serving graph, so serving applies identical transforms
Trainer, TunerTrain and tune
EvaluatorTensorFlow Model Analysis: metrics overall and by slice; "blesses" the model only if it beats thresholds or the current model
InfraValidator, PusherCheck the model loads and serves; push blessed models to serving

Validating data and models

  • Data validation: schema (types, required columns), ranges, null rates, category values, distribution shifts against training statistics. Stop the pipeline on failure instead of training on bad data.
  • Model validation: compare the candidate with thresholds and with the current production model, overall and per slice (region, device, demographic group) to catch hidden regressions and fairness issues. Only then register or deploy.
  • Infrastructure validation: the model loads in the serving container and answers within latency limits.

2. Retraining and CI/CD/CT

Retraining policy

TriggerGood forRisk
Schedule (daily, weekly)Steady data change; simple to runRetrains when nothing changed (cost) or too late when things change fast
New data volume (for example every 100k labelled rows)Label arrival drives valueNeeds data counting
Monitoring alert (drift or skew above threshold)Retrain when inputs changeDrift doesn't always hurt accuracy
Performance drop on ground truthRetrain when it mattersLabels may arrive weeks late
On demand (code change)New features or architectureThrough CI/CD, not by hand
Choose the policy from how fast the world changes, how soon labels arrive, and what retraining costs. Always gate an automatic retrain with evaluation against the current model before it reaches users.

CI/CD/CT

PracticeMeaning in MLGoogle Cloud pieces
Continuous integration (CI)On every commit: unit-test components and data checks, build containers, compile the pipelineCloud Build triggers on the repository, Artifact Registry for images and pipeline templates
Continuous delivery (CD)Deploy the new pipeline (and, after validation, models) to staging then productionCloud Build, Cloud Deploy, approvals
Continuous training (CT)The pipeline itself retrains on schedule or triggerPipeline schedules, Cloud Scheduler, Pub/Sub or Eventarc triggers, Cloud Run functions

Google's MLOps maturity levels: level 0 is manual notebooks and hand deployment; level 1 automates training with a pipeline (CT); level 2 automates the pipeline's own build, test and deployment (CI/CD of the pipeline).

4. Lab: a Kubeflow pipeline with a validation gate

  1. Create three lightweight components: validate_data (checks row count and nulls), train, and evaluate (returns a metric).
  2. Wire them with conditions so training only runs when validation passes, and registration happens only when the metric beats the current production model.
  3. Compile to YAML, submit with PipelineJob(enable_caching=True), then re-run unchanged and watch cached steps skip.
  4. Open the lineage view for the resulting model and trace it back to the dataset and run parameters.
  5. Add a Cloud Build trigger that runs component unit tests and recompiles the pipeline on each commit.
  6. Create a weekly schedule for the pipeline; then delete the schedule.

10. Common gotchas in one list

  1. Agent Platform Pipelines for ML lineage; Airflow for data-platform orchestration.
  2. Never auto-deploy without an evaluation gate against the current model.
  3. Retraining policy follows the data: schedules, data volume, drift or performance triggers.
  4. Late labels mean you can't wait for accuracy drops; use drift and schedules.
  5. CI tests code and builds images; CT retrains; CD deploys.
  6. Caching needs deterministic inputs.
  7. Validate data before training; schema changes otherwise train garbage.
  8. Build containers in CI and tag by commit for reproducibility.
  9. Composer is now Managed Service for Apache Airflow; the gcloud composer commands remain.
