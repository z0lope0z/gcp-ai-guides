1. Why LLM evaluation is different

Classic models have one right label per input. Generative outputs are open-ended: many answers can be right, wording varies run to run, and quality has several dimensions (correct, grounded, safe, helpful, on-format). So evaluation combines several kinds of metric over a fixed, versioned dataset, and runs on every change.

WhenPurpose
Model or tier selectionWhich model meets the quality bar at the lowest cost?
Prompt and RAG iterationDid this change help or hurt?
Before every release (CI)Regression gate: prompt, model version, retrieval or tool changes
After tuningTuned model vs base model with prompting, on held-out data
In productionOnline monitoring of sampled traffic, user feedback, safety

2. Building the evaluation dataset

  • Representative: sample real user questions (after removing PII), covering intents, languages and difficulty.
  • Edge and adversarial cases: out-of-scope questions, ambiguous requests, prompt-injection attempts, questions the documents don't answer.
  • References where possible: expected answers, expected source documents (for RAG), expected tool calls (for agents).
  • Size: dozens for quick iteration, hundreds for release decisions; more for small differences (see the win-rate calculator).
  • Versioned and frozen: store in Cloud Storage or BigQuery; never tune prompts on the final test split.
  • Add every production failure you find to the dataset (it becomes a regression test).

High ROUGE doesn't mean a good summary: a summary can share many words with the reference and still get the key fact wrong. Use overlap metrics as a cheap signal alongside model-based or human judgement.

4. Pointwise, pairwise and rubrics

ModeHowUse when
PointwiseJudge scores one response on a scale (for example 1–5) against criteriaAbsolute quality tracking, thresholds, monitoring
PairwiseJudge picks the better of two responses (baseline vs candidate) for the same prompt; report win rateComparing two models, prompts or settings; more sensitive to small differences
RubricsA list of specific, checkable criteria ("mentions the 30-day limit", "doesn't promise refunds for shipping")Making judgements consistent and explainable
Adaptive rubricsAgent Platform Evals generates prompt-specific rubrics, then checks responses against themDiverse prompts where one generic rubric is too vague
"Which of two prompt versions is better for open-ended answers with no single reference?" → pairwise model-based evaluation on a fixed dataset, calibrated against human ratings.

5. LLM-as-a-judge: biases and how to control them

BiasWhat happensMitigation
Position biasPairwise judge prefers the first (or second) responseEvaluate both orders and average or count only consistent wins; randomize order
Verbosity biasLonger answers win regardless of qualityRubrics that reward concision; length-controlled comparisons; check length vs score correlation
Self-preferenceA judge favours outputs from its own model familyUse a different (often stronger) judge model; validate with humans
Leniency / score compressionEverything gets 4/5Clear rubrics with anchored examples per score; prefer pairwise or binary checks
InconsistencySame input, different scoreLow judge temperature, multiple samples, explanations before scores
Domain blind spotsJudge lacks domain knowledge (medical, legal)Give references or context to the judge; expert human review

Validating the judge

  1. Have humans label a sample (for example 100–200 items) with the same rubric.
  2. Measure agreement between judge and humans: accuracy, and Cohen's kappa (agreement corrected for chance), or correlation for scores.
  3. Iterate on the judge prompt and rubric until agreement is acceptable; recheck when the judge model changes.

Kappa interpretation (rough): below 0.4 weak, 0.4–0.6 moderate, 0.6–0.8 substantial, above 0.8 strong. Use the calculator below.

6. Agent Platform Evals

Agent Platform Evals (formerly the Gen AI evaluation service) runs evaluations of models, prompts, RAG systems and agents.

Model-based metricsPrebuilt pointwise and pairwise templates (fluency, coherence, safety, groundedness, instruction following, summarization and question-answering quality) and custom criteria

# Sketch with the Agent Platform SDK; module and metric names vary by release.
import pandas as pd
import vertexai
from vertexai.evaluation import EvalTask, PointwiseMetric, MetricPromptTemplateExamples

vertexai.init(project="PROJECT_ID", location="us-central1")
data = pd.DataFrame({"prompt": prompts, "response": responses, "reference": references})
task = EvalTask(dataset=data,
                metrics=["exact_match", "rouge_l_sum",
                         MetricPromptTemplateExamples.Pointwise.GROUNDEDNESS],
                experiment="support-bot-eval")
result = task.evaluate()
print(result.summary_metrics)
SDK surfaces for evaluation move between modules across releases, and some modes (for example pairwise) are only in some client libraries. Learn the concepts: dataset, metrics (computation and model-based), pointwise vs pairwise, experiments for tracking.

7. Evaluating agents: trajectories and tool use

For agents, the final answer isn't enough: the trajectory (sequence of tool calls) shows whether the agent got there safely and efficiently.

MetricPasses when
Trajectory exact matchTool calls exactly equal the reference sequence
In-order matchAll reference calls appear in order; extra calls allowed
Any-order matchAll reference calls appear, in any order
Trajectory precisionShare of predicted calls that are in the reference (penalizes unnecessary calls)
Trajectory recallShare of reference calls that the agent made (penalizes missed steps)
Single tool useA specific required tool was called
Tool-call validity and parameter matchCalls are well-formed with correct arguments
Final response qualityModel-based metrics on the answer
Multi-turn task successThe user's goal was achieved over a whole conversation (often with a simulated user)
Exact = same calls, same order, nothing extra. In-order = same order, extras OK. Any-order = all present. Precision punishes extras; recall punishes misses.

8. Safety evaluation and red-teaming

  • Red-teaming: deliberately try jailbreaks, prompt injection (direct and through documents or tools), harmful requests, data exfiltration and PII leakage before launch.
  • Safety metrics: model-based safety scores, policy-violation rates, refusal rates on harmful prompts, over-refusal rates on benign prompts.
  • Track both under-blocking (harmful content gets through) and over-blocking (legitimate users refused).
  • Fairness: compare quality and refusal rates across languages, dialects and user groups.
  • Controls under test: safety filters, Model Armor templates, system instructions, tool permissions.

10. Regression testing in CI/CD

  1. Store prompts, model version, retrieval settings and tools in version control.
  2. On every change, a pipeline (Cloud Build or a Pipelines run) generates responses for the frozen evaluation set.
  3. Compute computation-based checks (schema, exact match, tool calls) and model-based metrics; compare with the current production baseline.
  4. Gate: block the release if key metrics drop beyond a tolerance or safety checks fail.
  5. Log the run to Experiments for history; pin model versions so upgrades are deliberate and evaluated.

12. Lab: evaluate two prompt versions and an agent

  1. Build a 50-row dataset from realistic questions with references (and expected sources for RAG).
  2. Run prompt A and prompt B. Compute exact match or ROUGE where references fit, and a pointwise groundedness or instruction-following metric.
  3. Run a pairwise comparison of A vs B; then swap the response order and rerun. How many verdicts flip (position bias)?
  4. Label 40 rows yourself; compute judge–human kappa with the calculator.
  5. For an ADK agent, write expected tool trajectories for 10 tasks; compute exact, in-order and any-order match, precision and recall.
  6. Wire the evaluation into a Cloud Build step that fails when groundedness drops by more than a set tolerance.

18. Common gotchas in one list

  1. Open-ended outputs need model-based or human evaluation; exact match and BLEU alone mislead.
  2. Pairwise for comparisons, pointwise for tracking.
  3. Validate the judge against humans before trusting it; measure agreement with kappa.
  4. Swap order in pairwise judging to cancel position bias.
  5. Long answers aren't better answers: watch verbosity bias.
  6. Don't let a model judge itself when you can avoid it.
  7. Small win margins on small sets are noise: compute an interval.
  8. Evaluate agent trajectories, not just final answers.
  9. Precision punishes extra tool calls; recall punishes missed ones.
  10. Frozen, versioned datasets with edge cases and past failures; run in CI on every change.
  11. Pin model versions so upgrades go through evaluation.
  12. Safety evaluation measures over-refusal too, not just harmful content.
  13. High ROUGE can hide wrong facts.
  14. Offline evaluation doesn't replace online monitoring and user feedback.
