1. The exam at a glance, and the 2026 renames

The Professional Machine Learning Engineer (PMLE) exam tests whether you can choose and operate the right Google Cloud service for each stage of an ML system, for both classic predictive ML and generative AI (gen AI). It's a design-and-judgement exam: the guide states that it doesn't directly assess coding, but you should be able to read Python and SQL snippets.

Validity2 years, then recertify

2. How to read Google scenario questions

Most questions describe a company, a constraint and a goal, then offer four designs that would all work in some sense. The right one is the design that meets the binding constraint with the least custom work.

  1. Underline the constraint. Typical ones: "minimal code" or "analysts know SQL", "lowest latency", "lowest cost", "data must not leave the VPC", "must explain each prediction", "small labelled dataset", "fastest time to market".
  2. Climb the managed ladder from the bottom. Prebuilt API → BigQuery ML or AutoML → foundation model (prompting, then grounding, then tuning) → custom training on Agent Platform → self-managed on GKE or Compute Engine. Stop at the first rung that meets every requirement.
  3. Move code to the data. If the data is in BigQuery, BigQuery ML or a BigQuery-sourced pipeline beats exporting CSVs.
  4. Prefer the managed service over DIY (Agent Platform Pipelines over Airflow-running-scripts-on-VMs, Model Monitoring over a cron job that compares histograms), unless the question rules it out.
  5. Eliminate the over-engineered and the under-powered. A custom TPU training job for 10,000 rows of tabular data is wrong; so is AutoML when the team needs a custom loss function.
"API, SQL, Auto, Tune, Custom, DIY." The ladder from least to most effort. The exam usually wants the lowest rung that satisfies every stated requirement.
"Technically correct but more work" is the most common wrong answer. If two answers both work, pick the more managed one that keeps data where it is.

3. Low-code models: BigQuery ML and AutoML (objective 1.1)

BigQuery ML

BigQuery ML (BQML) trains and runs models with SQL, inside BigQuery. The data never leaves the warehouse, analysts don't need Python, and prediction runs over whole tables. It's the default answer when "the data is in BigQuery" and "the team knows SQL".

-- Train: the TRANSFORM clause stores preprocessing with the model,
-- so ML.PREDICT applies exactly the same steps at prediction time.
CREATE OR REPLACE MODEL `shop.churn_model`
TRANSFORM(
  ML.STANDARD_SCALER(tenure_days) OVER () AS tenure_scaled,
  ML.QUANTILE_BUCKETIZE(monthly_spend, 10) OVER () AS spend_bucket,
  plan_type,
  churned
)
OPTIONS(
  model_type = 'BOOSTED_TREE_CLASSIFIER',
  input_label_cols = ['churned'],
  auto_class_weights = TRUE,
  data_split_method = 'AUTO_SPLIT',
  enable_global_explain = TRUE,
  model_registry = 'VERTEX_AI'            -- also register it in Model Registry
) AS
SELECT tenure_days, monthly_spend, plan_type, churned
FROM `shop.customers`
WHERE signup_date < '2026-01-01';

SELECT * FROM ML.EVALUATE(MODEL `shop.churn_model`);          -- precision, recall, roc_auc, log_loss...
SELECT * FROM ML.GLOBAL_EXPLAIN(MODEL `shop.churn_model`);    -- which features matter overall
SELECT * FROM ML.PREDICT(MODEL `shop.churn_model`,
                         (SELECT * FROM `shop.customers_today`));
SELECT * FROM ML.EXPLAIN_PREDICT(MODEL `shop.churn_model`,    -- per-row attributions
                         (SELECT * FROM `shop.customers_today`), STRUCT(3 AS top_k_features));

ML.FORECAST, ML.EXPLAIN_FORECASTFuture values with prediction intervals; trend/seasonality decomposition

Fine-tuning Gemini from BigQuery

BQML can supervised-tune a Gemini model on prompt/response pairs stored in a table, then serve it as a remote model, all from SQL:

CREATE OR REPLACE MODEL `support.ticket_tagger`
  REMOTE WITH CONNECTION `us.vertex_conn`
  OPTIONS (
    endpoint = 'gemini-2.5-flash',          -- base model to tune
    max_iterations = 300,
    prompt_col = 'prompt',
    input_label_cols = ['label']
  ) AS
SELECT prompt, label FROM `support.labelled_examples`;

SELECT * FROM ML.GENERATE_TEXT(MODEL `support.ticket_tagger`,
  (SELECT ticket_text AS prompt FROM `support.new_tickets`),
  STRUCT(0.0 AS temperature, TRUE AS flatten_json_output));
Supported base models, option names and the newer AI.GENERATE* functions change often. Check the BigQuery ML documentation for your release. The pattern to remember: a connection (a BigQuery connection resource whose service account has Agent Platform access), a remote model, and generation functions run over tables.

AutoML on Agent Platform

AutoML trains a high-quality model from labelled data with no model code: it searches architectures and hyperparameters for you. You pay in node hours and give up control of the architecture and loss.

Exporting BigQuery data to CSV to train elsewhere is almost never the answer when BQML or a BigQuery-sourced AutoML dataset meets the requirements. And AutoML isn't free of cost: it's often more expensive than a simple BQML model; the trade is accuracy and zero model code.

Feature engineering essentials

  • Leakage: a feature that wouldn't exist at prediction time (for example "refund issued" when predicting fraud) gives great offline metrics and useless production results.
  • Splits: split time-series data by time (train on the past, test on the future), and keep all rows of one user in one split, or the model memorizes users.
  • Imbalance: use class weights, resampling, or metrics such as PR AUC instead of accuracy.
  • Missing values and outliers: impute consistently in training and serving; clip or transform heavy tails (log).
  • Categoricals: one-hot for few values, embeddings or hashing for many; feature crosses for interactions in linear models.
  • Scaling: standardize numeric features for linear models and neural networks; tree models don't need it.

Feature Store on Agent Platform

The Feature Store lets teams define features once and reuse them for training and serving, which removes a major source of training-serving skew. The current version is BigQuery-native:

  • Feature data stays in BigQuery (tables or views). A feature group registers a BigQuery source and its features.
  • Offline: training data comes from BigQuery with point-in-time correct lookups (feature values as they were at each label's timestamp), avoiding leakage.
  • Online: an online store with feature views syncs selected features for low-latency serving. Bigtable online serving suits large data; optimized online serving gives the lowest latency and supports embedding (vector) retrieval.
  • Sync on a schedule or continuously; serve with FetchFeatureValues by entity ID.
The older "legacy" Feature Store (featurestores, entity types, its own storage) still appears in study material. New designs use the BigQuery-backed version.

Security and collaboration best practices

  • Run the notebook as a dedicated service account with least privilege; for personal instances use single-user access (end-user credentials) so actions are attributable.
  • No public IP, a private VPC subnet, and VPC Service Controls around sensitive projects; reach Google APIs through Private Google Access.
  • CMEK on disks when required; never store keys or passwords in notebooks: use Secret Manager.
  • Idle shutdown to stop paying for forgotten GPUs.
  • Keep code in Git (Workbench has a Git extension); move reusable code into packages and pipelines rather than sharing notebooks by email.
  • Admins standardize runtimes with Colab Enterprise runtime templates or Workbench custom container images.

Frameworks and models

Both environments come with TensorFlow, PyTorch, scikit-learn, XGBoost and JAX images, plus the Agent Platform SDK. From a notebook you can call Gemini, deploy open models from Model Garden for experiments, or open a Model Garden model card's sample notebook directly in Colab Enterprise.

A notebook is a prototyping tool, not a production system. "Schedule the notebook to retrain nightly in production" loses to a pipeline with validation, lineage and alerting, except for genuinely lightweight reporting jobs.

10. Training and tuning on Google Cloud (objective 3.2)

Organizing and ingesting training data

  • Tabular: BigQuery tables, read by AutoML and pipelines directly, or by custom code through the BigQuery Storage Read API (fast parallel reads into TensorFlow, PyTorch or pandas).
  • Unstructured: files in Cloud Storage plus a manifest. Custom training jobs see buckets as local paths through Cloud Storage FUSE (/gcs/my-bucket/...).
  • Managed datasets on Agent Platform hold image, video and tabular datasets with labels and splits, used by AutoML and for lineage.
  • Ingest from other systems with Dataflow, Datastream (database change data capture into BigQuery), Storage Transfer Service, or BigQuery Data Transfer Service.

Hyperparameter tuning

Hyperparameter tuning jobs (powered by Vizier) run many trials of your training code with different values and optimize a metric your code reports (with the cloudml-hypertune helper or the metric reporting API).

  • Algorithms: Bayesian optimization (default), grid search, random search.
  • max_trial_count bounds cost; parallel_trial_count trades wall-clock time against quality: more parallel trials finish sooner, but Bayesian search learns less from earlier trials.
  • Use log scaling for learning rates, discrete values for layer counts, and early stopping of poor trials.
  • Simple alternatives: AutoML (tunes for you), BQML num_trials with hyperparameter ranges.

Fine-tuning foundation models

OptionUse
Supervised tuning of Gemini on Agent Platform (or from BigQuery ML)Managed, parameter-efficient tuning on JSONL prompt/response pairs; the tuned model gets its own endpoint
Open models from Model Garden (Gemma, Llama) with LoRA / QLoRA notebooks or managed tuningFull control of weights; deploy where you want
Reinforcement learning / preference tuningAlign to human preferences
Consider tuning only when prompting and grounding fall short and you have good labelled examples. Benefits: higher quality on a narrow task, shorter prompts (cheaper, faster), consistent format. Costs: data preparation, tuning jobs, re-tuning when the base model is updated, and evaluation work.

Containers

Prebuilt prediction containers serve TensorFlow SavedModel, PyTorch, scikit-learn and XGBoost artifacts from Cloud Storage with no server code. A custom container is needed for other frameworks or custom logic. It must:

  • Run an HTTP server on the port in AIP_HTTP_PORT (default 8080).
  • Answer health checks on AIP_HEALTH_ROUTE and predictions on AIP_PREDICT_ROUTE.
  • Accept {"instances": [...]} and return {"predictions": [...]}.
  • Load model files from AIP_STORAGE_URI, and live in Artifact Registry.

Custom prediction routines (CPR) let you add preprocessing and postprocessing in Python (a Predictor class with preprocess, predict, postprocess) and build the container for you, so you don't write a web server.

Model Registry and versions

  • Each upload is a model version under one model; aliases (default, champion, challenger) point to versions.
  • Register models from custom training, AutoML and BigQuery ML (model_registry='VERTEX_AI'); attach evaluations; deploy any version to an endpoint.

Autoscaling and hardware

  • min_replica_count keeps capacity warm (latency on spikes, but you pay for it). max_replica_count caps cost.
  • Autoscaling follows CPU or accelerator duty cycle against a target (default about 60%), or request metrics on newer options. Scale-out takes minutes, so set the minimum for your baseline and expected surges.
  • Some endpoint configurations can scale to zero; check current support. Otherwise the minimum replica bills continuously.
  • GPUs for large deep models and LLMs; CPUs for trees and small models (cheaper per prediction at low volume); TPUs for high-throughput LLM serving.
  • Several models can share one machine with deployment resource pools (co-hosting) to cut cost for low-traffic models.

Making models faster and cheaper to serve

TechniqueEffect

Serving features

Online models need the same features they were trained with, fresh enough, in milliseconds. Fetch them from Feature Store online serving by entity ID (keyed on user, product, device), or compute request-time features in the request itself. Streaming features flow through Pub/Sub and Dataflow into the store.

Joining BigQuery at request time for features is too slow for low-latency serving. Precompute into the online store.

Regex for patterns, SDP for PII, Armor for prompts, filters for harm, VPC-SC for exfiltration. Pick the narrowest tool that matches the threat in the question.

Responsible AI

  • Bias enters through unrepresentative data, historical labels and proxies (ZIP code standing in for race). Evaluate metrics per slice and compare groups with fairness metrics such as demographic parity, equal opportunity (equal recall) and equalized odds.
  • Mitigate: collect better data, reweight or resample, remove proxies, adjust thresholds per policy, and document decisions in model cards and datasheets.
  • Monitor fairness in production, not only at launch; review gen AI outputs with safety evaluations and red-teaming.

18. Monitoring and troubleshooting (objective 6.2)

What can go wrong after launch

ProblemMeaningDetect with
Training-serving skewProduction input distribution differs from the training data (often a preprocessing bug or a different source)Model Monitoring with the training dataset as baseline
Data (prediction) driftProduction inputs change over time compared with an earlier production windowModel Monitoring comparing recent windows
Concept driftThe relationship between inputs and label changes (fraudsters adapt); inputs may look the sameGround-truth performance tracking (needs labels): precision/recall over time
Feature attribution driftThe features the model relies on change importanceModel Monitoring with Explainable AI enabled
Operational issuesLatency, errors, saturation, costCloud Monitoring metrics and alerts, Cloud Logging, request-response logging to BigQuery

Model Monitoring on Agent Platform

  • Attach a monitor to a model version (Model Monitoring v2) or an endpoint; it works on endpoints, batch inference and models served elsewhere if you supply the data.
  • Choose the baseline: training data for skew, or a past production window for drift.
  • Choose the features, a distance measure (L-infinity for categorical, Jensen-Shannon divergence for numeric), thresholds per feature, a sampling rate and a schedule (monitoring interval).
  • Alerts go to email, Cloud Monitoring notification channels or Pub/Sub (which can trigger a retraining pipeline).
  • Request-response logging to BigQuery provides the raw data for analysis and for joining with labels later.
Model Monitoring v1 (endpoint-centric jobs) and v2 (model-centric monitors) both appear in material; default thresholds and APIs differ by version. Learn skew vs drift vs attribution drift and what each baseline is.

Monitoring and testing gen AI

  • Log prompts, responses, latency, token counts, safety ratings and user feedback (with PII controls).
  • Run the evaluation dataset on a schedule and on every prompt or model change (regression testing), using Agent Platform Evals with computation and LLM-as-a-judge metrics.
  • Track groundedness and hallucination rates for RAG, and refusal and safety-block rates.
  • Watch for model version changes: pin model versions in production and re-evaluate before moving to a new one.
  • Use Cloud Trace and logging for agent and tool-call traces; Model Armor findings flow to Security Command Center.

Troubleshooting order

  1. Did the system break? Errors, latency, quota, a deployment change, a missing feature.
  2. Did the inputs change? Skew (pipeline bug) vs drift (world changed).
  3. Did the relationship change? Concept drift, confirmed with fresh labels.
  4. Fix the cause: repair preprocessing for skew; retrain on recent data for drift and concept drift; add features if the world changed in a way the model can't see.
Retraining doesn't fix training-serving skew caused by a bug: the new model trains on the same correct data and is served the same broken inputs. Fix the serving pipeline.

19. Hands-on labs

Five short labs that cover the most-tested workflows. Use a sandbox project with billing alerts. Placeholders: PROJECT_ID, BUCKET, region us-central1.

Endpoints bill for every hour a replica is deployed, even with no traffic. Finish each lab with its clean-up step.
Lab 1: Churn model end to end in BigQuery ML
  1. Load a public dataset into a dataset of your own (for example a public e-commerce or telco churn table), or create a customers table with a label column.
  2. Train a logistic regression baseline, then a boosted tree model with a TRANSFORM clause, as in section 3.
  3. Compare with ML.EVALUATE; inspect ML.CONFUSION_MATRIX at thresholds 0.3, 0.5 and 0.7, and pick one with the threshold calculator.
  4. Run ML.EXPLAIN_PREDICT on five rows and ML.GLOBAL_EXPLAIN; write down the top three features.
  5. Retrain with model_registry='VERTEX_AI' and find the model in Model Registry.

You should be able to say: why TRANSFORM prevents skew, why PR AUC beats accuracy here, and how batch scoring avoids an endpoint. Clean up: DROP MODEL; delete the dataset.

Lab 2: Custom training, registry and a canary rollout
  1. Write a scikit-learn or XGBoost script that reads from BigQuery, trains, and saves model.joblib (or model.bst) to AIP_MODEL_DIR.
  2. Run it as a custom training job with a prebuilt container (section 10).
  3. Upload the artifact as model version 1 with a prebuilt prediction container; create an endpoint and deploy with min 1, max 2 replicas.
  4. Change one hyperparameter, train version 2, deploy it to the same endpoint with --traffic-split=0=10,...=90, and send 100 requests. Check the split in the endpoint's metrics.
  5. Roll back: set version 1 to 100%, then undeploy version 2.

Clean up: undeploy all models, delete the endpoint (gcloud ai endpoints undeploy-model, gcloud ai endpoints delete).

Lab 3: A Kubeflow pipeline with a validation gate
  1. Create three lightweight components: validate_data (checks row count and nulls), train, and evaluate (returns a metric).
  2. Wire them with a condition so training only runs when validation passes, and registration only happens when the metric beats a parameter.
  3. Compile to YAML, submit with PipelineJob(enable_caching=True), then re-run unchanged and watch cached steps skip.
  4. Open the lineage view for the resulting model: trace it back to the dataset and the run parameters.
  5. Create a weekly schedule for the pipeline; then delete the schedule.
Lab 4: Model Monitoring and drift
  1. Using the endpoint from lab 2, enable request-response logging and create a model monitor with the training table as baseline, a short interval and low thresholds.
  2. Send normal traffic, then traffic with one feature shifted (for example multiply monthly_spend by 3).
  3. Find the skew alert; identify which feature crossed its threshold and the distance value.
  4. Explain whether this is skew or drift, and what you'd do if it were a pipeline bug vs a real market change.
Lab 5: A grounded, guarded Gemini app
  1. In Agent Studio or a notebook, prompt a Flash-tier model to answer questions about a set of internal PDFs. Note the hallucinations.
  2. Create a RAG Engine corpus (or Agent Search data store) from the PDFs and ground the same prompts; compare answers and citations.
  3. Set safety settings (harm categories and thresholds), and put Model Armor in front of prompts and responses; try a prompt-injection string and a fake credit-card number.
  4. Build a 20-question evaluation set and run a pointwise groundedness metric and a pairwise comparison of the ungrounded vs grounded versions with Agent Platform Evals.
  5. Measure latency and token counts; try context caching for a long shared document.

Clean up: delete the corpus or data store and any Model Armor templates.

25. Common gotchas in one list

  1. Lowest rung that meets every requirement: prebuilt API, then BigQuery ML or AutoML, then Gemini, then custom training. More custom work is the usual wrong answer.
  2. Old and new names are the same product: Vertex AI = Agent Platform; Cloud Composer = Managed Service for Apache Airflow; Cloud DLP = Sensitive Data Protection.
  3. Data in BigQuery and a SQL team means BigQuery ML; don't export to CSV.
  4. Accuracy is meaningless on imbalanced data; use precision, recall, F1 or PR AUC, and pick the threshold from the business cost.
  5. Precision when false positives hurt, recall when false negatives hurt.
  6. Fresh or private facts need grounding (RAG), not fine-tuning. Tune for behaviour, format and narrow tasks.
  7. Skew compares with training data; drift compares with earlier production data; concept drift needs labels to see.
  8. Retraining doesn't fix skew caused by a serving bug. Fix the preprocessing.
  9. One preprocessing implementation for training and serving: TRANSFORM, TensorFlow Transform, in-model layers, Feature Store.
  10. Batch inference needs no endpoint; online endpoints bill per replica-hour even when idle.
  11. Canary = small traffic split on the same endpoint; keep the old version deployed for instant rollback.
  12. Private Service Connect endpoints keep traffic off the internet; VPC Service Controls stop exfiltration.
  13. Sampled Shapley for trees and non-differentiable models; Integrated Gradients for neural networks; XRAI for image regions.
  14. TPUs dislike custom ops and float64; GPUs are the flexible default for deep learning; CPUs for classic ML.
  15. Data parallel if the model fits on one device; model parallel if it doesn't. Fix input bottlenecks before adding GPUs.
  16. Training jobs run as a service account; permission errors are about that identity.
  17. Checkpoint when using Spot VMs or long jobs.
  18. Agent Platform Pipelines for ML workflows; Managed Airflow for broad data orchestration that may trigger ML pipelines.
  19. Gate automatic retraining with evaluation against the current model, overall and per slice.
  20. Model Armor for prompt injection and jailbreaks; safety filters for harmful content; SDP for PII; regex for fixed patterns.
  21. 429 errors on Gemini: exponential backoff, then Provisioned Throughput for steady production traffic.
  22. Batch and context caching cut Gemini cost; a smaller model tier cuts cost and latency.
  23. Split time series by time; random splits leak the future.
